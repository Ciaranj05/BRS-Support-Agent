# PAYMENTS – DECISION TREE

Use this when the issue relates to payments, refunds, payouts, billing, payment requests, failed payments, or payment allocation.

---

## 1. INITIAL TRIAGE

IF multiple users are affected:
→ Escalate immediately (possible wider system or payment issue).

IF single user:
→ Identify issue type:
- Booking payment
- Membership / bill payment
- Missing payment
- Refund
- Payment failure
- Payout / reporting
- Payment request

If the user clearly asks about a refund, go directly to the REFUND section. Do not give generic refund instructions.

---

## 2. BOOKING PAYMENT STATUS

IF user mentions booking payment status:

Ask:
“What colour payment symbol is showing on the booking?”

→ GREEN:
Fully paid

→ BLUE:
Part paid
→ Check total vs amount paid

→ RED:
Unpaid
→ Open booking → Payments tab

→ YELLOW:
Overpaid
→ Check for:
- Removed players
- Booking changes
- Price updates

Then guide:

Go to:
Tee Sheet >> Tee Time >> Booking Details >> Payments tab

Then:
- Open the tee time
- Open the booking details
- Expand the Payments tab

Follow-up:
“Is there a payment listed in the Payments tab? Yes or No”

---

## 3. PAYMENT NOT SHOWING / CUSTOMER SAYS THEY PAID

This is a priority scenario.

Guide system checks immediately:

Go to:
Tools >> BRS Payments >> Transactions

Then:
- Open the booking or bill first
- Check the Payments tab
- Search Transactions by amount
- Search Transactions by date
- Search using customer name or booking/bill reference if available

---

### OUTCOME A — PAYMENT EXISTS

→ Likely mismatch or allocation issue.

Next steps:
- Check allocation
- Check “Left to Allocate”
- Confirm correct booking / bill

IF mismatch remains:
→ Escalate.

---

### OUTCOME B — NO PAYMENT IN BRS, USER CONFIRMS MONEY TAKEN

→ Escalate immediately.

Do NOT:
- Ask for further proof
- Assume bank transfer
- Continue troubleshooting

Use:

“I understand — that’s frustrating.

Since there’s no record in BRS, this needs to be checked with the payments platform.

I can raise this with support now.”

---

### OUTCOME C — NO PAYMENT IN BRS, USER UNSURE

Ask ONE question:

“Can the customer confirm if the payment has actually left their account? Yes or No”

→ If YES:
Escalate.

→ If NO:
Advise retry payment.

→ If unsure:
Ask them to check bank / card statement.

---

## 4. REFUND

IF asked “How do I refund a booking?” or any booking/customer refund question:

Give the detailed BRS Payments refund pathway below.

Go to:
Tee Sheet >> Tee Time >> Booking Details >> Payments tab

Then:
- From the tee sheet, click the tee time to open the Booking Details screen
- Expand the Payments tab
- Find the correct online payment
- Confirm the payment is the correct one to refund
- Click Refund
- The system will populate the full refundable amount automatically
- For a partial refund, manually enter the amount to be refunded
- Click Refund to send the payment back to the customer

Important:
- Always confirm the correct booking and payment before clicking Refund
- Refunds can be full or partial
- Partial refunds require the refund amount to be entered manually
- Online refunds go back to the original card
- Refunds usually take 5–10 days to appear in the customer account
- Online payments completed through BRS Payments should show a Refund button when eligible

To review refund records:

Go to:
Tools >> BRS Payments >> Refunds

Then:
- Search/review the refund record
- Confirm the refund date and amount

IF there is no Refund button:
- Confirm the payment was taken through BRS Payments
- Confirm the payment is eligible for online refund
- If the club does not use BRS Payments, follow the offline/non-BRS Payments refund process
- Escalate if the payment should be refundable but no refund option is available

IF the refund is offline:
- Offline refunds may include cash, PDQ, or cheque
- The money must be returned outside BRS
- Do not tell the customer the money has been returned unless the offline refund has actually been completed

IF customer says refund has not arrived:
- Check Tools >> BRS Payments >> Refunds
- Confirm the refund exists
- Confirm the refund date
- Confirm the correct payment was refunded
- Advise the normal 5–10 day timeframe
- Escalate if outside normal timeframe or disputed

Do not:
- Give generic “log in and find booking” instructions
- Say “Cancel and Refund” unless that is the exact available action
- Tell the user BRS automatically notifies the customer unless confirmed
- Tell the user a refund has completed unless it has actually been processed

---

## 5. PAYMENT FAILURE

IF multiple users affected:
→ Escalate.

IF single user:

Then:
- Retry payment
- Check card details
- Try alternative method

IF repeated failures:
→ Escalate.

---

## 6. PAYMENT ALLOCATION / BILL ISSUES

IF payment exists but bill or booking is incorrect:

Check:
- Payment exists
- Allocation
- “Left to Allocate” = 0

IF still incorrect:
→ Escalate.

---

## 7. PAYOUT QUERY

Go to:
Tools >> BRS Payments >> Payouts

Then explain:
- Shows when funds are paid into bank
- Includes fees
- Based on rolling schedule

IF figures do not match after checking breakdown:
→ Escalate.

---

## 8. VAT REPORT QUERY

Go to:
Tools >> BRS Payments >> VAT Reports

Then explain:
- Gross sales
- Fees
- Net sales
- VAT breakdown

---

## 9. PAYMENT REQUESTS

IF booking-related:

Go to:
Tee Sheet >> Booking >> Payments >> New Booking Payment

IF not booking-related:

Go to:
Tools >> BRS Payments >> General Payment Requests

---

## 10. ESCALATION TRIGGERS

Escalate if:

- No payment in BRS but money taken
- Payment mismatch remains
- Refund unclear or disputed
- Refund does not appear after the normal 5–10 day timeframe
- Refund button is missing when the payment should be eligible
- Multiple payment failures occur
- Reporting discrepancy remains
- Customer disputes payment

---

## KEY BEHAVIOUR

Always:

✔ Check BRS first
✔ Guide to exact location in system
✔ Use BRS navigation labels
✔ Ask only when needed
✔ Escalate when conditions are met
✔ Confirm before processing a refund
✔ Refund against the correct payment only

Never:

❌ Assume external payment
❌ Manually mark as paid
❌ Continue after escalation condition
❌ Ask unnecessary follow-up questions
❌ Give generic refund steps when the user asks about BRS booking refunds
❌ Say a refund is complete unless it has actually been processed
