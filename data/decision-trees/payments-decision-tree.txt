# PAYMENTS – DECISION TREE

Use this when the issue relates to payments, refunds, payouts, or billing.

---

## 1. INITIAL TRIAGE

IF multiple users are affected:
→ Escalate immediately (possible wider system or payment issue)

IF single user:
→ Identify issue type:
- Booking payment
- Membership / bill payment
- Missing payment
- Refund
- Payment failure
- Payout / reporting

---

## 2. BOOKING PAYMENT STATUS

IF user mentions booking payment status:

Ask:
“What colour payment symbol is showing on the booking?”

→ GREEN:
Fully paid

→ BLUE:
Part paid  
→ Check total vs amount paid

→ RED:
Unpaid  
→ Open booking → Payments tab

→ YELLOW:
Overpaid  
→ Check for:
- Removed players
- Booking changes
- Price updates

Then guide:

1. Click tee time  
2. Open booking  
3. Open Payments tab  

Follow-up:
“Is there a payment listed in the Payments tab?”

---

## 3. PAYMENT NOT SHOWING / CUSTOMER SAYS THEY PAID

This is a priority scenario.

Guide system checks immediately:

1. Open booking or bill  
2. Check Payments tab  
3. Go to:
   Tools >> BRS Payments >> Transactions  
4. Search by:
   - Amount  
   - Date  
   - Customer name  

---

### OUTCOME A — PAYMENT EXISTS

→ Likely mismatch or allocation issue  

Next steps:
1. Check allocation  
2. Check “Left to Allocate”  
3. Confirm correct booking / bill  

IF mismatch remains:
→ Escalate  

---

### OUTCOME B — NO PAYMENT IN BRS, USER CONFIRMS MONEY TAKEN

→ Escalate immediately  

Do NOT:
- Ask for further proof  
- Assume bank transfer  
- Continue troubleshooting  

Use:

“I understand — that’s frustrating.

Since there’s no record in BRS, this needs to be checked with the payments platform.

I can raise this with support now.”

---

### OUTCOME C — NO PAYMENT IN BRS, USER UNSURE

Ask ONE question:

“Can the customer confirm if the payment has actually left their account?”

→ If YES:
Escalate  

→ If NO:
Advise retry payment  

→ If unsure:
Ask to check bank / card statement  

---

## 4. REFUND

Ask:
“Is this a full or partial refund?”

Then:

1. Open booking  
2. Go to Payments  
3. Select correct payment  
4. Click Refund  
5. Choose amount  
6. Confirm  

Then clarify:

IF payment was online:
→ Refund goes to original card (5–10 days)

IF offline:
→ Refund must be processed outside BRS  

Important:
→ Always confirm before refunding  
→ Always refund against correct payment  

---

## 5. PAYMENT FAILURE

IF multiple users affected:
→ Escalate  

IF single user:

Steps:
1. Retry payment  
2. Check card details  
3. Try alternative method  

IF repeated failures:
→ Escalate  

---

## 6. PAYMENT ALLOCATION / BILL ISSUES

IF payment exists but bill or booking is incorrect:

Check:

1. Payment exists  
2. Allocation  
3. “Left to Allocate” = 0  

IF still incorrect:
→ Escalate  

---

## 7. PAYOUT QUERY

Guide:

Tools >> BRS Payments >> Payouts  

Explain:

- Shows when funds are paid into bank  
- Includes fees  
- Based on rolling schedule  

IF figures do not match after checking breakdown:
→ Escalate  

---

## 8. VAT REPORT QUERY

Guide:

Tools >> BRS Payments >> VAT Reports  

Explain:

- Gross sales  
- Fees  
- Net sales  
- VAT breakdown  

---

## 9. PAYMENT REQUESTS

IF booking-related:

→ Booking → Payments → New Booking Payment  

IF not booking-related:

→ Tools >> BRS Payments >> General Payment Requests  

---

## 10. ESCALATION TRIGGERS

Escalate if:

- No payment in BRS but money taken  
- Payment mismatch remains  
- Refund unclear or disputed  
- Multiple payment failures  
- Reporting discrepancy  
- Customer dispute  

---

## KEY BEHAVIOUR

Always:

✔ Check BRS first  
✔ Guide to exact location in system  
✔ Ask only when needed  
✔ Escalate when conditions are met  

Never:

❌ Assume external payment  
❌ Manually mark as paid  
❌ Continue after escalation condition  
❌ Ask unnecessary follow-up questions
